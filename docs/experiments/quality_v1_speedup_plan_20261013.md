## 优先方案与具体步骤

1. 权重按版本同步：FSDPVLLMShardingManager每次generate入口导出state_dict，MetaX sync_model_weights将完整权重写临时safetensors、RPC加载并reset_prefix_cache；共用代码哈希与冻结manifest一致。同一参数更新前权重固定，改为policy_version首次生成同步，只有成功优化器更新或加载checkpoint才改变版本并使缓存失效。同一候选收集期复用推理权重与同版本前缀缓存；模型卸载/恢复与真实版本变化分离。先保留原CPU卸载行为，仅跳过重复导出/加载/清缓存，再验证同版本多轮常驻，概率重算/参数更新前释放显存；失败时禁止继续生成。

2. 动作边界原生停止：生成遇到完整search/answer结束标记就停，保留结束标记，继续执行相同解析/协议/质量检查，不生成随后伪造information或第二动作。仅合法首动作可触发停止；文本编码token与原生token前缀必须一致，正确计入概率及损失。停止会改变原始采样流和异常尾部行为，应记录新生成协议版本，不宣称逐轨迹与旧 run 完全相同。当前未设这些stop字符串。

3. 先排除已训练question_id，再生成G8；若改变随机流或原候选顺序，明确记录采样版本。再可利用P池历史candidate记录挑选此前k3–6及相邻难度且未训练题，提高当前候选命中；保留20%均匀探索，更新后必须重新跑当前policy的G8判定，旧轨迹/旧分数不得直接用于GRPO。本步骤改变候选分布，需独立实验组；所有数据仅来自原P训练池，禁止访问D/T/正式测试标签。

## 验收与收益边界

先完成CPU状态/缓存失效/异常恢复与动作token对齐测试，再在隔离分支固定checkpoint40、固定P题目/种子按单因素做3–5步GPU短跑；不混写原run。测总步耗时、同一policy同步次数、导出/搬运/检索/解码分项、生成总token与有效token、合格率、训练组数、GPU峰值、有限数值、实际优化器更新、异常率及D256 EM。

每步保持32组×8、合格范围3–6、奖励/协议/重复惩罚、原上下文/动作预算、每rank两次实际优化器更新；若变更其中任一项必须独立记录为实验变量。G8→G4无法直接沿用answer_correct_3_6；降低train_batch_size的短step也不等于相同训练量更快。
