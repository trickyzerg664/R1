# R1：SFT 冷启动是否改善后续 RL

版本：2026-10-03；状态：实验构思与执行计划，尚未实现新增代码、生成数据或启动训练。负责人：Codex。

本轮只研究用户的第 1 个问题。SFT/RL 数据重叠比例实验留到后续；本计划先固定两阶段题目互斥，减少干扰因素。

## 1. 判断与研究问题

建议在当前 Qwen2.5-7B Base 上尝试少量、高质量、符合检索交互协议的 SFT 冷启动。优先验证它是否提高早期有效回答比例、减少无效工具调用、加快 RL 达到相同留出集表现；最终正确率是否更高，需要对照实验，不能预设。

DeepSeek-R1 在 RL 前使用少量高质量示例作冷启动，论文同时证明直接从 Base 做 RL 可行。[DeepSeek-R1](https://arxiv.org/html/2501.12948v1#S2.SS3.SSS1)

Search-R1 的 Base/Instruct 比较观察到 Instruct 起点较高、收敛较快，而训练后最终表现相近。这为检索任务的冷启动提供方向性依据，但通用 Instruct 模型与本项目自建检索 SFT 数据不同，不能作为本实验结论。[Search-R1 §5.2](https://arxiv.org/html/2503.09516v1#S5.SS2)

SFT 的泛化效果受示例质量、优化程度和基础模型能力影响，不能简单认定 SFT 只能记忆或必然提高泛化。[Rethinking Generalization in Reasoning SFT](https://arxiv.org/abs/2604.06628)

预注册三个问题：

1. **效果**：相同 RL 更新预算下，SFT→RL 是否优于 Base→RL？
2. **贡献**：SFT→RL 相比 SFT-only 的追加收益有多大？
3. **效率**：计入 SFT、示例生成与检索成本后，达到同一开发集分数是否更便宜或更快？

对当前项目的假设：冷启动主要改善前期协议执行和答案完整性。上一轮观察中，直接 RL 已将自然完成答案比例从约 89.84% 提高到 99.22%，因此更应关注达到此水平的成本和留出集正确率，不能只看格式指标。

## 2. 核心对照

所有模型从同一 Qwen2.5-7B Base 权重、同一 tokenizer 出发。

| 组别 | 训练流程 | 用途 |
| --- | --- | --- |
| C0 | Base，无新增训练 | 原始能力与格式基线 |
| C1 | Base→SFT | 测量 SFT 本身的收益 |
| C2 | Base→RL | 直接 RL 对照 |
| C3 | Base→同一 SFT 检查点→RL | 测量冷启动后的完整流程 |

核心差值：C3−C2 为完整冷启动流程收益，C3−C1 为 RL 在 SFT 后的追加收益，C1−C0 为 SFT 自身收益。三个差值分别报告，避免把 SFT 提升误记为 RL 提升。

同一个种子下 C1 与 C3 共用同一个 SFT 检查点。C2/C3 使用完全相同的 RL 题池、源数据顺序种子、更新配置和停止规则；模型生成结果和动态筛选结果允许自然不同，必须记录这些不同。

当前 v4 可以作为历史参考或符合条件的首个 C2。复用前核对代码快照、P10000 哈希、奖励/长度/检索协议和末步产物；评测在同一新协议下重做。不能只因为都训练 100 步就认定可比较。若任何核心条件不同，新增独立 C2，保留旧实验历史。

## 3. 数据设计

**RL**：沿用冻结的 P10000，来自 NQ+HotpotQA。正式位置为 `/mnt/public/code/lyk/lzy/data/runs/formal-pdt-7b8-v1/P.parquet`。

**SFT**：从现有 NQ+HotpotQA 原训练 split 中，排除 P10000、整个 D1000、T2000 后取题，正式目标 1,000 道不同问题，NQ/HotpotQA 比例接近现有训练来源比例，约 47%/53%。先导使用其中嵌套的 256 题。按来源、问题长度和检索轮数分层，记录筛选前后分布，不只保留最短、最容易的问答。

跨集合先按稳定 question_id 和规范化文本去重，再检查明显改写及近重复。共享 Wikipedia 检索语料是任务条件；问答标注、演示轨迹和最终答案不能进入评测 prompt 或检索结果的人工附加文本。未知预训练污染只能说明不能完全排除，不能声称已清除。

**开发评价**：从已冻结 D1000 中预先分来源选 D256，复核问题、标准答案和明显近重复，冻结修订清单与版本。D32 沿用作历史诊断，原始分数和剔除已确认错误题的分数均保留。新 D256 为方案选择的主要依据，不能继续用 D32 的几题涨跌作最终判断。

**最终评价**：T2000 保持封存，模型、SFT 规模、评测方式和主要比较全部锁定后再统一评价 C0/C1/C2/C3。不能根据 T 结果再选 SFT 轮数、学习率、模型或重跑种子。标注复核先于观察被比较模型的输出，保留原标签和变更依据。

## 4. SFT 演示的内容与质量

目标是教会模型执行与当前 RL 相同的多轮检索问答流程：读取问题和当前可见信息，生成必要的推理、合法 `<search>` 调用，读取真实 `<information>`，最终输出完整 `<answer>`。

主方案采用 **C0 自生成、验证后筛选的轨迹**，固定模型和生成协议；先用独立 64 题探针评估合格率和成本，每题最多 8 次尝试。每题最多保留一条合格完整轨迹。需要同时满足：奖励判分正确、答案被可见证据支持、工具标签闭合、工具调用真实执行、无被迫结束、无答案缺失；人工按来源及长度分层复核至少 10%，不能仅凭最终奖励为 1 就认定过程正确。

若自生成轨迹质量或合格题数不足，先报告不足，不悄悄改用训练过的 v4 或其他教师。使用更强教师会增加蒸馏因素，应单独登记教师来源、是否接触过训练/评测数据及生成成本，并在数据冻结前形成新版本。教师生成可以改变提示，但学生训练仍使用原有 RL prompt；教师的 few-shot 示例、答案提示等不能被带入学生输入。

每条原始轨迹保存问题 ID、模型及协议哈希、生成 seed、各轮可见输入、输出、检索查询、返回文档 ID、判分、证据检查和人工审查状态。演示不是只含最终答案的普通 QA，也不通过人为添加长思考文本制造训练目标。

## 5. SFT 的实现约定和拟定参数

多轮检索轨迹转为逐次模型调用的训练样本：输入为该轮实际可见的有界历史，目标为该轮 assistant 输出。复用当前上下文裁剪与观察截取逻辑，不能把完整长对话随意截为 4,096 token 后继续当完整轨迹。

- system/user、检索观察、无效动作反馈、padding 的 loss mask 为 0；模型生成的推理、搜索请求和最终答案才参与预测损失。
- 检索文本作为上下文保留，不要求模型预测工具返回文本。逐轮 mask 与标签边界必须在 tokenizer 后验证。
- 多轮题会展开成多个样本。记录“不同问题数 / 完整轨迹数 / 展开样本数 / 有效目标 token 数”，使用按问题均衡的权重，避免轮数多的题自动得到更多权重。
- 正式初始方案：1,000 题、每题 1 条轨迹、1 epoch、全参数 SFT。先导为 256 题、1 epoch，属于链路和方向检查，不能直接充当正式结果。
- 拟定学习率 5e-6、warmup 5%、grad_clip=1；全局 batch=32 个展开样本、micro batch=8；开启梯度检查点。实际优化步数由展开样本数决定，不能把 1,000 题写成 1,000 步。
- 采用与已验证 RL 一致的 FP16 运算、FP32 主权重及显式梯度缩放思路。SFT 入口需要独立验证精度、缩放、卸载和导出，不能直接沿用 RL 的通过记录。
- 参数属于待验证起点，不宣称最优。显存不足时先调整卸载和微批/累积，保持各对照的实际全局 batch 和有效数据预算一致；变更后重新冻结协议。

首轮固定规模和一轮训练，不同时搜索多种教师、SFT 轮数、LoRA、奖励或长度。若结果值得继续，再单独做 SFT 剂量或 epoch 消融。

## 6. RL 保持的条件

沿用当前 G8 动态筛选：每题 8 条轨迹，每周期保留 8 道有效题（64 轨迹），最多 8 轮候选补抽；最多 100 个训练周期。mini/micro=32/8，lr=1e-6、warmup10、初始 scaler16；safe_v1 损失、FP32 主权重、optimizer/ref 卸载及 token 分块设置保持一致。

保持 prompt4096、start256、每轮生成256、观察2048、max_turns10、同一检索索引/编码器/topk3/超时、回答边界和二值正确性奖励，不增加新的格式奖励。所有候选轨迹都在线重新生成，不用 SFT 教师输出充当 RL rollout。

每组 reference 冻结为 **该 RL 阶段开始时的 actor**：C2 是 Base，C3 是对应 SFT 权重；这样两组初始 KL 都接近零，并采用同一“约束相对阶段起点”的规则。权重不同，因此 C3−C2 的主结论是整个冷启动流程效果；若要单独区分 reference 的贡献，后续增加 C3 固定 Base-reference 消融，首轮不混入。

SFT 后启动全新的 RL optimizer、scheduler、scaler、采样游标和随机流，绝不继承 SFT Adam 状态或 v4 的 RL 训练状态。C1 的权重与 tokenizer 导出后检查完整性和重新加载一致性，再启动 C3。

动态筛选可能把 SFT 后已全对的候选组丢弃。必须分别记录 K0/K1…K8、候选数、有效组、保留率、补抽轮数和实际训练问题数；训练奖励上升不能替代留出集收益。凑不齐有效问题则按原规则停止并报告，不降低标准、补旧轨迹或静默延长预算。

## 7. 评价和公平比较

**主要效果指标**：末步在同一 T 上的答案 EM（规范化后的精确匹配），分别报告总体、NQ、HotpotQA。主解码为 do_sample=false、temperature=0、每题一条完整检索轨迹，所有模型复用相同检索协议。

**开发曲线**：Base、SFT 完成后，以及 RL 的已保存 step20/40/60/80/100。统一离线评价 D256，不修改正在运行 v4 的实时评价配置。先导两组 RL 均保存 step5/10/20/25，按同一规则评价；这些新步骤只属于未来先导。

**过程指标**：自然答案完成率、答案标签有效率、有效搜索率、错误/重复查询、检索次数、生成 token、观察裁剪、单轮长度上限命中、强制结束、梯度/scaler/更新跳过、相对阶段起点的 KL。不同 reference 的 KL 不能直接当作相同绝对基准；必要时在固定探针上额外比较相对共同 Base 的变化。

**成本**：分别记录 SFT 训练、教师生成/拒绝尝试、人工审查、RL 全部候选生成（含丢弃）、检索和评价。记录整机 GPU 占用小时、检索 CPU/服务时间、墙钟时间及 token；不能用“有效更新只花 21 秒”代替整机占用成本。可同时报告重复训练时摊销数据制作成本的情景，但完整成本必须保留。

主比较固定 RL 周期和协议，成本差异单独报告。效率比较绘制开发 EM 对累计成本，SFT 曲线从其真实前置成本开始；不能只计 RL 部分。只有双方都达到的预先设定分数阈值才比较达到该分数的成本；未达到写“未达到”。若 SFT 的额外成本影响结论，再预先锁定同整机预算的直接 RL 延长对照，不把固定 100 步对照称为等总成本对照。

评价使用同一道题的成对差值，报告正确数、错→对/对→错、95% 配对区间和各来源结果。正式比较采用 3 个训练种子（42/43/44），每个种子内部共用同一 SFT 权重供 C1/C3；分别报告跨种子波动，不把 3 个种子说成充分证明普遍规律。SFT 题目清单先固定，训练随机种子改变；数据切分敏感性留到后续。

效果的实用提升目标先设为 +2 个百分点；“效果更好”要求 C3−C2 的留出集区间支持正向差异，同时审查来源是否明显退步。若正确率无明确提升而同分成本降低，可只认定效率收益。T2000 未必能检出 +2 pp，小样本/低统计功效时结论为未确定，不将无显著差异写成等效。

## 8. 分阶段执行顺序与验收

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0：静态准备 | 冻结研究问题、C0/P/D/T/源码，分层选 SFT 题，审核 D256；核实当前任务资源 | 不同题集互斥、清单/版本齐全，主指标和比较先登记 |
| P1：数据探针 | 64 题自生成及过程审查，估算 256/1,000 题演示成本 | 合格率、尝试成本与失败原因可追踪；教师和数据标准冻结 |
| P2：SFT 链路 | 补齐 dataset/mask/精度/保存接口；CPU 验证；独立小批 GPU 更新和导出加载 | 环境文本不参与 loss、梯度有限、更新有效、导出可重新加载、短问答可运行 |
| P3：先导 | 256 题 SFT；C2/C3 各 25 个 RL 周期，seed42；评价 C0/C1/C2/C3 | 完成链路、候选筛选/成本均记录；不能仅凭 D256 少量题变化判定最终优劣 |
| P4：正式 | 1,000 题 SFT；C2/C3 各最多100周期，3种子 | 同预算条件可核对，末步与恢复产物完整，全部失败/不足批次保留 |
| P5：锁定与最终评价 | 锁定模型及协议后统一评价 T，生成四组效果/成本/逐题表 | 完整回答三个研究问题，未达到/失败/未确定明确标记 |

先导阶段一共需要一个 SFT 训练及两条 25 周期 RL 训练，C0/C1 只是评价。按上一轮约 30.6 分钟/周期，50 个 RL 周期粗估约 25.5 小时整机占用，另加数据制作、SFT、保存和评价。正式两条 100 周期 RL ×3 种子共 600 周期，按该速度约 306 小时（12.8 天），可因冷启动后的筛选和检索时间变化而明显改变。该估算不是新实验实测；当前服务器已有训练，执行时不抢占、不重启当前任务。

先导若发生格式或数值失败，先修链路再继续；若 SFT 明显伤害开发表现，复查轨迹质量、mask、上下文及优化强度并版本化记录。先导未显示显著提升不能直接否定冷启动。任何更改方案的结果不覆盖原计划和失败记录。

## 9. 当前实现状态与后续改动范围

本次静态检查发现：`verl/trainer/fsdp_sft_trainer.py` 导入 `SFTDataset`，但 `verl/utils/dataset/__init__.py` 仅导出 RLHFDataset/RMDataset，仓库中没有找到 `class SFTDataset`；SFT 入口的 FSDP/autocast 写死 BF16；现有通用 SFT 配置默认 max_length1024、4 epoch。当前 SFT 入口不能视为可直接用于本实验。

拟定职责：数据筛选/manifest/逐轮转换集中在独立冷启动实验模块；SFT dataset 负责 token/role/loss mask；精度、缩放和导出留在 SFT trainer 的明确配置接口；已有 RL trainer 只读取 SFT 导出的初始化权重和 reference。尽量复用当前 generation/context/reward 实现，不复制第二套检索/判分逻辑，不改当前在线 RL 主循环。

实施前 CPU 验证应覆盖：问题去重与隔离、所有 token mask 的移位、工具返回不计损失、逐轮可见上下文、按问题权重、padding、数据顺序可复现及导出清单。GPU 验收覆盖真实 FP16 更新、scaler、卸载显存、导出重载和 SFT→RL 接续。CPU 模拟结果不能代替 GPU 验收。

实验实际启动时才创建唯一 run_id、运行记录和配置快照，产物放独立 runs 目录。每阶段按项目要求同步方案、运行记录与进度台账。本次只形成方案与静态核查依据，未运行 CPU/GPU 测试，也未改生产代码。
